# Дополнительные пакеты агентов и возможностей

Статус: реализовано в цикле разработки версии v2.3.0 в рамках задачи #3612.

## Цель

Базовая сборка приложения Marinara Engine не должна ни компилировать, ни поставлять реализации дополнительных агентов и возможностей. Новая установка начинает работу вообще без дополнительных пакетов. При обновлении сохраняются те возможности, которые были доступны до появления системы пакетов.

Официальный каталог, исходный код пакетов, воспроизводимые артефакты, скрипты проверки и порядок работы над правками собраны в репозитории [Pasta-Devs/Marinara-Agents](https://github.com/Pasta-Devs/Marinara-Agents). Установленные артефакты лежат внутри указанной папки данных приложения Marinara, поэтому обновления приложения не могут их перезаписать.

## Модель пакета

Пакет агента может добавлять одного или нескольких декларативных агентов, а также дополнительные доверенные исполняемые возможности:

- серверные точки входа для маршрутов, хуков жизненного цикла, источников промптов, обработчиков результата и миграций хранилища;
- клиентские точки входа для панелей, областей чата, разделов настроек, вариантов первоначальной настройки и элементов отображения во время работы;
- общие схемы JSON и стабильные контракты передачи данных;
- принадлежащие пакету файлы ресурсов, документацию и фрагменты знаний для Professor Mari.

Пакеты рассчитаны на версионированный API возможностей приложения Marinara. Импортировать закрытые пути исходного кода движка им запрещено.

Клиентские элементы возможностей получают выбранную локаль интерфейса движка через атрибуты `lang` и `dir`, а также
через объект `capabilityProps.localization`. Интерфейсы, принадлежащие пакету, хранят собственные файлы локалей и при
отсутствии перевода откатываются на английский язык пакета; движок не переводит ни промпты пакета, ни машинные
значения, заданные пакетом. При смене локали используется то же событие `marinara-capability-props`, поэтому
установленный интерфейс перерисовывается без перезапуска движка.

### Доставка и кеширование

Файлы установленных пакетов отдаются с надежными валидаторами, полученными из хешей SHA-256 каждого файла в манифесте. Эти же значения Engine использует для повторной проверки байтов при каждом чтении. Клиентский пакет (`/api/capability-packages/<id>/client`) и все ресурсы пакета всегда проходят повторную валидацию (`no-cache` вместе с `ETag`), поэтому неизменившийся файл отвечает `304 Not Modified`, а не скачивается заново, а повторно опубликованный файл подхватывается сразу. Ничто не отдается как `immutable`: правила установки разрешают повторно публиковать ту же версию с другими байтами, поэтому адреса пакетов не зависят от содержимого.

API возможностей 1.1 добавляет универсальный фасад среды выполнения в контекст
активации на сервере. Пакеты могут читать текущее состояние отладки агентов и
писать в журнал сервера через логгер Pino движка, в том числе принудительно
включая режим отладки, без импорта закрытых модулей логирования и настройки
среды выполнения. Фасад дает набор операций, а не сами объекты движка.

API возможностей 1.2 добавляет операции с чатами и сообщениями в рамках
транзакции, точечную запись метаданных чата и проверку существования записей
лорбука, а также хранилище совместимости для пространственных снимков. Пакеты
могут проверять изменения предметной области внутри транзакции движка и
атомарно сохранять метаданные вместе с сообщением-владельцем, свайпом или
пространственным снимком, не получая при этом ни дескриптор базы данных, ни
объект таблицы. За откат и совместимость с историческим хранилищем отвечает
движок, за проверку и правила предметной области – пакет. Тот же API отдает
нормализованные записи чатов и персонажей, выбор подходящих записей лорбука,
разбор ответов в формате, близком к JSON, и вызовы языковой модели с уже
разрешенными настройками. Учетные данные подключений, реализации провайдеров,
дескрипторы базы данных и объекты хранилища остаются закрытыми внутри движка.

### Ветки чата в API возможностей 1.7

API возможностей 1.7 добавляет в `CapabilityChatRecord` нормализованные метаданные ветки:

```ts
branch: {
  title: string | null;
  parentChatId: string | null;
  parentMessageId: string | null;
  childMessageId: string | null;
} | null;
```

`title` – это сохраненное название ветки без пробелов по краям. Корневые чаты
возвращают `null`. Для веток, которые создал сам движок, доступны прямой
родительский чат, исходное сообщение развилки и скопированное дочернее
сообщение. У пустых веток привязки к сообщениям равны null. Устаревшие ветки,
испорченные метаданные и импортированные соседние чаты группы без известной
связи возвращают null в полях происхождения: движок не восстанавливает прежние
связи по догадкам. Обычный экспорт и импорт не переносят идентификаторы
родителя и сообщений, потому что при переносе между установками они меняются.
Удаление родителя не затрагивает происхождение дочерней ветки.

### Возможности Game Experience в API 1.8

API возможностей 1.8 добавляет Game Experience из пакетов, контекст промпта для каждого хода Game и запись ресурсов.

Пакет может предоставить целый Game Mode, а не дополнение к встроенному режиму. Он объявляет слот `game-surface` и выбирается при создании игры в блоке Experiences мастера настройки. Выбор записывается в игру и остается неизменным до ее конца, поэтому Experience не переключается посреди прохождения. Поверхность рисует собственные HUD, меню и бой поверх общей истории и объявляет, какие встроенные системы она заменяет. Все необъявленное остается встроенным, поэтому Experience отключает только то, что действительно реализует. Необязательное поле `contributions.gameSurface.surfaceClass` называет класс, который Engine применяет к области игры, пока поверхность подключена. Таблица стилей пакета может благодаря этому менять общий интерфейс, который рисуется за пределами собственного элемента.

Пакеты с разрешением `prompt-context` добавляют текст в системный промпт каждого созданного хода Game. Пакет с живым состоянием может так согласовать модель с тем, что видит игрок. Вклад может также объявить заменяемые встроенные игровые системы; Engine перестает указывать модели управлять ими. Вклады собираются для каждого хода и никогда не обязательны: пустой результат пропускается, а ошибка или превышение срока записывается в журнал и пропускается без влияния на генерацию.

Фасад ресурсов добавляет запись к чтению, поэтому настройка пакета может найти или создать Persona игрока и ее лорбук. Хранение, валидация и идентификаторы остаются у Engine; содержимое предметной области остается у пакета.

### Ресурсы пакета в API возможностей 1.10

API возможностей 1.10 добавляет общую доставку статических ресурсов пакета. Манифест может объявить `contributions.assets.paths` - список разрешенных изображений (`png`/`webp`/`gif`/`jpg`/`jpeg`) и файлов JSON внутри пакета, не более 256. Engine отдает их по адресу `/api/capability-packages/<id>/assets/<path>` через ту же цепочку проверки, что применяется к значкам вкладки: удержание пути в пределах пакета, наличие хеша в `files[]`, список разрешенных пассивных типов содержимого и повторная проверка целостности при каждом чтении. Схема отвергает активные типы документов (SVG, HTML и скрипты); у каждого объявленного пути должен быть закрепленный хеш в `files[]`; внутренний файл `manifest.json` пакета нельзя отдать даже после объявления. Для `contributions.assets` требуется манифест с `schemaVersion` 2 и `capabilityApi` 1.10 или новее; манифест v1 вообще не может его объявить. Ресурсы всегда проверяются повторно: как и клиентский пакет, они несут надежный `ETag` на основе хеша манифеста и отвечают на неизменившуюся проверку кодом `304 Not Modified` без тела. Набор тайлов скачивается снова, только если его байты действительно изменились. Ответы намеренно никогда не получают `immutable`, поскольку правила установки разрешают повторно опубликовать ту же версию с другими байтами, и адрес с номером версии не зависит от содержимого. Так Experience `game-surface` может поставлять настоящую графику, а не встраивать ее в клиентский пакет.

Манифест с нарушением этих правил отклоняется при установке одним из сообщений: "A declared package asset must be listed in the package file manifest", "contributions.assets requires schemaVersion 2 and capabilityApi 1.10 or newer", ошибкой расширения схемы для пути, который не ведет к изображению или JSON, либо, если имена в архиве отличаются только регистром и превратятся в один файл в файловой системе без учета регистра, "Package contains duplicate file" / "Package manifest declares files that collide on case-insensitive filesystems".

Каждый элемент возможности получает для этого свои идентификаторы: `capabilityProps.packageId` и `capabilityProps.packageVersion` приходят вместе с `localization`. Пакет строит адреса ресурсов в виде `/api/capability-packages/<packageId>/assets/<path>`, при необходимости добавляя `?v=<packageVersion>`, чтобы новая версия сбросила промежуточный кеш. Повторно загружать список установленных пакетов или разбирать собственный адрес импорта не нужно.

### Интерфейс боя Experience в API возможностей 1.11

API возможностей 1.11 добавляет интерфейс боя в свойства возможности `game-surface`. `combatActive` сообщает точный момент, когда встроенный интерфейс боя действительно подключается. В отличие от него, `chatMeta.gameActiveState`, сюжетное состояние сцены GM, отстает от переключения и может указывать "combat", когда столкновения еще нет. `combatStyle` передает действующий стиль (`classic` или `tactical`). `requestCombat()` просит Engine создать столкновение тем же путем, что и кнопка Start Combat, но без окна подтверждения, поскольку собственный интерфейс Experience уже выразил намерение. Процесс генерации Engine по-прежнему решает, каким будет столкновение. Способа напрямую передать из пакета участников или состояние боя намеренно нет: бой остается под управлением Engine.

`requestCombat()` сохраняет стабильную идентичность, не показывает уведомлений на стороне пакета и возвращает код, по которому Experience рисует собственный ответ: `"started"` или отказ `"combat-active"`, `"pending"` (генерация уже идет), `"no-turn"` (GM еще не написал ход) либо `"unavailable"` (завершенная сессия или повтор). `combatPending` и `combatError` отражают ход и ошибку генерации, поэтому после сбоя пакет не остается ждать `combatActive`. Как интерфейсы 1.7 и 1.8, но в отличие от жестко ограниченного `contributions.assets` из 1.10, эти свойства передаются всем пакетам `game-surface` независимо от объявленного `capabilityApi`. Метка 1.11 показывает время их появления; пакет, которому они нужны, объявляет 1.11, и старый Engine корректно его отвергает.

### Пространственные события для владеющего Experience в API 1.12

API возможностей 1.12 адресует пространственные события еще и пакету Experience, которому принадлежит игра. `spatial_transition_committed`, `spatial_transition_rejected` и нетипизированный сигнал `spatial_context_refresh`, прежде адресованные только `hierarchical-maps` в событии окна `marinara-capability-server-event`, теперь дополнительно отправляются с `packageId`, равным `gameExperienceId` чата. Полезная нагрузка различается: подтвержденное событие несет `{ chatId, commandId, currentLocationId, definitionRevision, travel? }`; отклоненное несет `{ chatId, commandId, code?, message? }` без полей места, поскольку перемещения не было; сигнал обновления несет `data: null`. Experience, отправивший команду путешествия через аргумент `pendingSpatialTransition` функции `sendMessage`, может подтвердить или убрать путешествие сразу после того, как хост узнает результат, а не выводить его из последующих чтений. Версия 1.12 закрывает и пробел в World Maps: переходы, отклоненные на одном из двух тихих путей HTTP, при подтверждении хода владельца до потока во время генерации или при отдельном подтверждении REST, раньше вообще не создавали события. Теперь оба пути создают `spatial_transition_rejected` только при окончательном доказательстве, то есть коде ошибки `spatial_*`, отличном от `already_applied`. Неоднозначные сбои, например сетевая ошибка, при которой мог потеряться ответ об успешном подтверждении, вместо этого отправляют нетипизированный сигнал `spatial_context_refresh`. Получатели сверяются с сервером, а не принимают выдуманный результат. Подтвержденное событие с `travel.mode` равным `"step_by_step"` и `complete: false` означает, что путешествие продолжается; сохраняйте ожидание до завершающего события. Это мягкий интерфейс, как 1.11: события приходят независимо от объявленного `capabilityApi`. Объявляйте 1.12, только если пакет от него зависит.

### Временное сворачивание повествования в API возможностей 1.13

API возможностей 1.13 добавляет `requestsCollapsedNarration` в объявление интерфейса, которое пакет `game-surface` передает в `setExperienceChrome`. Пока флаг равен true, блок повествования Game Mode сворачивается до узкой ручки, чтобы Experience мог освободить экран для заставки или полноэкранного эпизода.

Это ЗАПРОС, а не настройка. Выбранное игроком состояние сворачивания никогда не записывается, а флаг действует только пока Experience является активной поверхностью. Уберите флаг или перестаньте быть активной поверхностью, и блок вернется в выбранное игроком состояние. Это гарантия, что после запроса он всегда откроется снова; пакет намеренно не может сохранить сворачивание навсегда.

Правила безопасности Engine важнее запроса. Блок принудительно открывается, когда на экране видно поле ввода игрока, в том числе в самом начале сцены до первого сегмента, и когда активны элементы перехода к следующему сегменту. Только через них можно закончить ход; пакет, способный их скрыть, мог бы навсегда заблокировать игрока. Ручка также продолжает показывать индикатор внимания при ожидающем повторе анализа сцены, генерации или генерации боя. Если игрок вручную открыл блок во время запроса, он остается открытым до конца запроса. Как 1.11 и 1.12, это мягкий интерфейс: поле действует независимо от объявленного `capabilityApi`. Метка 1.13 показывает время появления, поэтому зависящий от поля пакет объявляет 1.13.

### API возможностей 1.17: подготовка Experience перед первым ходом

Пакет `game-surface` может объявить `contributions.gameSurface.prepareBeforeStart: true` при версии схемы 2 и API возможностей 1.17. Engine монтирует эту поверхность, когда игра готова, до включения **Start Game** (начать игру). Классические игры и пакеты без этого флага сохраняют прежний порядок запуска.

Основная поверхность, включившая эту возможность, получает два дополнительных свойства:

- `startup: boolean` остается true, пока игрок не завершит вступление Engine кнопкой **Continue** (продолжить). Пока значение true, приостановите симуляцию мира и действия игрока.
- `setStartupReady(context: string | null): void` сообщает состояние подготовки. Передавайте `null` во время загрузки, сохранения или восстановления после сбоя. Передавайте строку только после того, как фактический мир надежно сохранен и пригоден к использованию; пустая строка разрешает запуск без дополнительного контекста.

Хост блокирует **Start Game**, подтверждение подготовки виджетов и повторные попытки первого хода до получения строки готовности. Во время блокировки собственный интерфейс загрузки и ошибки с повторной попыткой пакета остается видимым. После готовности пакет скрывается за обычным вступлением Engine. **Continue** открывает обычную поверхность, которая может монтироваться заново: сделайте подготовку мира идемпотентной и восстанавливайте сохраненное состояние вместо повторной генерации. Возврат к игре, вступление которой уже завершено, не повторяет начальную подготовку.

Контекст вступления ограничен **8 000 символами**. Некорректный или слишком большой контекст сохраняет блокировку запуска и показывает ошибку; хост не обрезает факты о мире. Передайте компактное описание подготовленной начальной локации и ее фактического состава персонажей. Engine добавляет этот текст к существующему `generationGuide` первого хода с источником `game_start`, чтобы вступление использовало уже существующий мир. Это не регистрирует контекст для последующих ходов; для них продолжайте использовать обычный вклад пакета в промпт или контекст генерации хода.

Обратные вызовы готовности относятся к смонтированному чату, игре и пакету. Запоздалые вызовы из другой области игнорируются. Сбой модуля или среды выполнения блокирует запуск, а не считает отсутствие контекста мира успехом. После перезагрузки пакет должен сообщать готовность на основе сохраненного мира. Серверный поставщик контекста промпта по-прежнему работает только на чтение и ограничен коротким сроком выполнения; не используйте его для генерации мира или длительной блокировки запуска.

### API возможностей 1.19: инструменты из пакетов

API возможностей 1.16 позволял пакету побудить модель что-то _сказать_, чтобы затем на это отреагировать. Эта версия позволяет модели что-то _вызвать_. Пакет с новым разрешением `tools` регистрирует именованный инструмент в серверной точке входа. Engine предлагает его вместе со встроенными инструментами на каждом ходе каждого чата, проверяет вызов по JSON Schema пакета и передает аргументы обработчику.

```ts
export async function activate({ api }) {
  api.registerTool({
    name: "set_time",
    description: "Move the world clock forward or back.",
    parameters: {
      type: "object",
      properties: {
        action: { type: "string", enum: ["advance", "rewind"] },
        minutes: { type: "integer", minimum: 0 },
      },
      required: ["action", "minutes"],
      additionalProperties: false,
    },
    handler: async (args, { chatId }) => {
      const clock = await moveClock(chatId, args.action, args.minutes);
      return { time: clock.label };
    },
  });
}
```

Вызовы инструментов выбраны вместо формата ответа намеренно. Формат занимает весь ответ: повествование пришлось бы поместить в поле JSON-объекта, и оно не могло бы поступать потоком. Вызов инструмента может идти рядом с текстом, пока модель пишет свой ход. Пакет получает аргументы, уже ограниченные провайдером, вместо извлечения их из готового повествования. Схема задает обязательные правила; соглашение лишь просит модель их соблюдать.

Разница особенно заметна с перечислениями. Если пакет знает двенадцать мест, он может внести их названия в схему. Тринадцатое название будет отклонено до передачи обработчику. Существующий валидатор аргументов Engine указывает допустимые значения, чтобы модель могла исправить вызов. Возвращенное обработчиком значение показывается модели как результат инструмента.

Перед созданием инструмента учитывайте следующие правила:

- Имена имеют вид `<packageId>_<name>`, где `-` заменяется на `_`: `set_time` из `world-clock` становится `world_clock_set_time`. Имя, уже занятое другим пакетом, отклоняется. Встроенные и включенные пользовательские инструменты сохраняют совпадающие имена; определение пакета не добавляется. Полное имя ограничено **64 символами**. Порядок одинаков для определений и выполнения: встроенный инструмент, пользовательский, инструмент пакета.
- Инструменты добавляются, пока пакет активен. Дополнительного переключателя для каждого чата, как у встроенных инструментов, нет: решение принимается выдачей разрешения и регистрацией. Выбранный провайдер должен поддерживать нативные вызовы инструментов.
- Схема параметров копируется и компилируется при регистрации. Если Engine не может ее скомпилировать, активация завершается ошибкой, заметной при разработке, а не посреди хода.
- Исключение обработчика помечает вызов как неудачный и записывается в журнал; его сообщение модели не передается. Через **10 секунд** без результата ход также перестает ждать. Обработчик продолжает работать, но больше не блокирует ход.
- Результат должен сериализоваться в объем не более **64 KiB**. Более крупный или несериализуемый результат приводит к ошибке вызова, а не вытесняет разговор из контекста. Описания и результаты считаются доверенным содержимым пакета. Проверяйте `chatId` перед чтением или изменением данных чата.
- Каждое определение сериализуется в запрос к провайдеру на каждом ходе и учитывается при подгонке контекста. Ограничения: **16 инструментов на пакет**, **64 во всех пакетах**, **512 символов** в описании и **8 KiB** в схеме параметров. Превышение вызывает исключение и срывает активацию. Повторная регистрация собственного имени заменяет инструмент без расхода дополнительного места.
- Контекст активации перестает работать после ее завершения. Если пакет сохранит `api` и позже вызовет `registerTool` из обратного вызова, регистрация будет отклонена. Завершенная среда не может регистрировать инструменты или заменять инструменты новой активации.
- Деактивация, обновление или удаление пакета освобождают его инструменты. Модель не получает инструмент, пакет которого уже не может ответить. Инструменты удаляются до ожидания очистки; каждый обратный вызов очистки ограничен 8 секундами.

Эти ограничения относятся только к асинхронному ожиданию. Пакеты выполняются как доверенный код в процессе сервера; таймер не может прервать синхронную работу, блокирующую цикл событий. Для принудительной отмены нужен отдельный рабочий поток или процесс; этот API такой изоляции не предоставляет.

`api.registerTool` существует только начиная с этой версии Engine. Пакет, которому он нужен, должен объявить `capabilityApi` 1.19 и откажется устанавливаться на более старой версии.

## Доверие и установка

Официальный каталог – это версионированный документ в формате JSON, который проверяется по схеме и загружается по HTTPS. Каждая запись выпуска содержит неизменяемые адреса артефактов, контрольные суммы SHA-256, размер в байтах, совместимость с движком, список разрешений и признак того, нужен ли перезапуск для его среды выполнения.

Команды модели, объявленные пакетом, выполняются только тогда, когда пакет объявляет `chat-write`, установлен и готов. Это разрешение также контролирует запись через API постоянного хранения пакета, включая сообщения, метаданные чата, события roleplay и снимки пространства. `chat-read` контролирует чтение чатов, сообщений, состояния игры и снимков пространства. Те же проверки действуют внутри транзакций хранения и блокировок чата; разрешение на запись не дает автоматически разрешение на чтение. Вызовы хранения, принадлежащие самому движку, остаются доверенными.

После установки подробный вид **Download Agents** (загрузка агентов) показывает разрешения, объявленные установленной версией. Если версия в каталоге запрашивает другие разрешения, они показаны отдельно. Установка или обновление кода по-прежнему требует существующего одобрения, привязанного к точной версии и контрольной сумме; команды модели не запрашивают отдельное одобрение на каждом ходе.

Это проверки API, а не изолированная среда JavaScript. Разрешения сети, хранилища и интерфейса являются декларациями доступа. Код пакета в браузере и на сервере остается доверенным кодом и может обращаться к среде хоста; устанавливайте только пакеты, которым доверяете. Проверяется готовность, а не возможность отдавать файлы, поэтому обновление, оставляющее пакет в состоянии `restart-required`, останавливает разрешение его команд до перезапуска движка.

При запуске сервера хост один раз загружает каталог, если установлен хотя бы один официальный пакет. Он выбирает только более новые версии, совместимые с работающим движком и API возможностей, проверяет их обычным конвейером установки и устанавливает до активации сред выполнения пакетов. Сбои изолированы: проблема с одним пакетом не затрагивает остальные. Когда каталог недоступен или проверка не прошла, уже имеющиеся файлы и состояние реестра продолжают работать, а при неудачной проверке готовности серверной среды выполнения включается откат на предыдущую версию.

Установщик обязан:

1. требовать привилегированного доступа через loopback или права администратора;
2. соблюдать HTTPS, ограничения на объем скачивания и тайм-ауты;
3. проверять доверие к каталогу и контрольную сумму SHA-256 артефакта до распаковки;
4. отклонять абсолютные пути, выход за пределы папки, ссылки, файлы устройств и незаявленные файлы;
5. проверять манифест и совместимость с движком;
6. распаковывать во временную папку рядом с целевой;
7. активировать пакет атомарно и только после успешной проверки;
8. сохранять предыдущую версию до успешного запуска новой среды выполнения;
9. откатывать активацию при сбое;
10. никогда не запускать скрипты установки, обновления и удаления.

Официальный каталог включает только доверенные исполняемые пакеты от самого проекта. Для сторонних пакетов в будущем понадобится отдельная, явно описанная модель доверия.

## Поведение во время работы и перезапуск

Реестром установленных пакетов владеет сервер, он же сообщает клиентам о доступных возможностях. Декларативные и перезагружаемые модули активируются сразу. После активации интерфейс сбрасывает кеш запросов каталога, агентов, возможностей режима и активного чата.

Манифест может объявлять `restartRequired` только тогда, когда хост не может безопасно перезагрузить эту точку входа. Успешная активация на ходу показывает `Agent installed. It is ready to use.` Активация с перезапуском показывает `Agent installed. Restart Marinara Engine to finish setup.`

Пакеты пошаговых игр перезагружаются на ходу: при установке их серверный движок и ручной запуск слеш-командой регистрируются сразу, а при удалении среда выполнения отключается без перезапуска движка. Настройки **Conversation Commands** (команды в режиме Conversation) для отдельного чата задают только то, может ли персонаж отправить скрытую команду пакета; на слеш-команду, которую вводите вы, они не влияют. В текущих официальных манифестах пошаговых игр осторожная устаревшая пометка о перезапуске сохраняется для совместимости с движком версии 2.x. Движок версии 3.x распознает тип `turn-game`, выполняет безопасную активацию на ходу и возвращает пакет как активный и готовый к работе.

## Миграция для совместимости

При первом запуске после обновления:

- пользовательские агенты остаются без изменений;
- каждый устаревший встроенный агент, видимый в этой установке, отмечается как установленный;
- карты, звонки в режиме Conversation и игры в режиме Conversation сохраняют прежнюю доступность;
- существующие настройки отдельных чатов, снимки, состояние игры, история звонков и память агентов остаются на месте;
- миграция идемпотентна и отмечается как завершенная только после того, как все записи о доступности устаревших возможностей надежно сохранены.

Артефакты устаревших пакетов остаются доступными в официальном каталоге как источники для миграции. В новой установке они не показываются и не активируются, пока вы их не установите.

## Удаление

Удаление убирает пакет из выбора в активных чатах, стирает настройки его агента и скачанные исполняемые файлы, а при необходимости отключает его среду выполнения при перезапуске. Прежние чаты, сообщения, снимки карт, сводки звонков и записи завершенных игр остаются доступными для чтения, поэтому удаление пакета не уничтожает вашу работу. Безвозвратное удаление исторических данных – это отдельное действие, которое вы выполняете сами.

Любое удаление требует подтверждения. Затронутые чаты возвращаются к обычным базовым экранам, и история при этом не портится.

## Интерфейс каталога

В панели **Agents** (агенты) есть элемент `Download Agents` – такой же, как `Download Cards` в разделе Card Browser. Он открывает адаптивную библиотеку на весь экран: поиск, типы пакетов, сведения о совместимости, состояние установки и обновления, разрешения, занимаемое место, документация и кнопки удаления.

На компьютере это список для просмотра и область с подробностями рядом. На телефоне – одна область с явной кнопкой возврата и крупными элементами под палец. Состояния "пусто", "нет сети", "несовместимо", "скачивание повреждено", "установка прервана", "доступно обновление", "выполнен откат" и "нужен перезапуск" проработаны как полноценные, а не как редкие исключения.

## Условие завершения выноса

Вынос считается завершенным только при выполнении всех условий: реализации пакета больше нет в рабочих сборках клиента и сервера, новая установка не может ее активировать без скачивания пакета, обновленная установка ее сохраняет, а установка, обновление и удаление пакета проходят на компьютере, на телефоне и в файловых системах, совместимых с Termux.

### API возможностей 1.20: наборы правил Game Mode

Набор содержит проверенные данные: поддерживаемое Engine разрешение проверок, лист из заданных элементов, отдых и указания GM. Зарезервированный ресурс `ruleset.json` обнаруживается как `gm-verbs.json`: через `contributions.assets.paths` и хеш в `files[]`.

```json
{
  "schemaVersion": 2,
  "capabilityApi": { "major": 1, "minor": 20 },
  "id": "ruleset-5e-2014",
  "kind": ["ruleset"],
  "permissions": [],
  "entrypoints": {},
  "contributions": { "assets": { "paths": ["ruleset.json"] } },
  "files": [{ "path": "ruleset.json", "sha256": "<sha256 of the file>", "bytes": 25767 }]
}
```

Пример показывает только поля набора; `name`, `version`, `description`, `engine` и `builtAgainst` обязательны. Разрешения, агент и точки входа клиента или сервера не нужны. Тип `ruleset` и `ruleset.json` требуют друг друга. Код и строковые выражения не исполняются; новая механика требует изменения Engine. Формат и пример 5e описаны в [`game-rulesets-and-sheets-implementation.md`](game-rulesets-and-sheets-implementation.md).

Манифест должен объявлять API 1.20; старый Engine откажет в установке. Engine отклоняет объявленный размер свыше 256 KB до чтения, повторно проверяет хеш и строгую схему `packages/shared/src/schemas/ruleset.schema.ts`. Неверный файл пропускается с одной записью журнала о пакете и первых ошибках `path: message`. При повторе ID выигрывает первый пакет по порядку ID пакетов; другой пропускается с записью журнала. `engine-legacy` и `traditional` зарезервированы.

Выбор один раз сохраняется в `chat.metadata.gameRuleset`. Без привязки действуют прежние правила. Отсутствующий пакет или старая версия делает набор недоступным, без подмены правил. Проверяются ID набора и пакет поставщика, чтобы другой пакет не перехватил игру повторением ID.

### API возможностей 1.21: каталоги

Каталоги предлагают готовые заклинания, способности классов и снаряжение в редакторе листа. Заголовок расположен в `catalogs` внутри `ruleset.json`; записи бывают встроенными или отдельным ресурсом:

```json
{
  "capabilityApi": { "major": 1, "minor": 21 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json", "catalogs/spells.json"] } },
  "files": [
    { "path": "ruleset.json", "sha256": "<sha256>", "bytes": 25767 },
    { "path": "catalogs/spells.json", "sha256": "<sha256>", "bytes": 418204 }
  ]
}
```

`catalogs/<id>.json` должен соответствовать ID своего каталога, а не другого. Требуются хеш в `files[]` и объявляющий его `ruleset.json`. Объявленный размер свыше 1 MB отклоняется до чтения. Встроенные и файловые записи проверяются относительно одного листа. Лимиты: 12 каталогов на набор, 2000 записей на каталог.

Клиент загружает содержимое при открытии выбора через `GET /api/capability-packages/rulesets/catalog?rulesetId=&catalogId=&version=`. Список установленных наборов содержит только количество записей. Текст каталога не добавляется в промпт автоматически; GM видит только выбранное через `gm.sheetSummary`. Ресурсы и поле `catalogs` в проверенном файле требуют API 1.21. Старая строгая схема отклонила бы файл целиком. Разрешения не нужны.

### API возможностей 1.22: блок battle

`battle` задает здоровье, необязательные MP, пулы ячеек и списки, чьи каталожные строки становятся `CombatSkill`. После боя значения возвращаются теми же операциями листа, что используются кнопками игрока.

```json
{
  "capabilityApi": { "major": 1, "minor": 22 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json"] } }
}
```

Это связь данных с боем Engine, а не полный адаптер настольной системы. Встроенные расчеты не читают `attackRoll`, `save`, `concentration` и `perCostStep`. Точные правила относятся к отдельному подключению адаптеров. `coverage.combat` имеет независимое значение и этой связью не читается. Проверенное содержимое `ruleset.json` требует API 1.22 для `battle`, как 1.21 для `catalogs`. Без разрешений и изменений наборов без блока.

### API возможностей 1.23: масштабируемые значения каталога

`scaled` позволяет набору поддерживать до четырех собственных числовых столбцов строки. Используются обычные ссылки на значения и необязательная таблица порогов, например ресурсы по уровню или использования по характеристике, без новых арифметических операций.

```json
{
  "capabilityApi": { "major": 1, "minor": 23 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json", "catalogs/spells.json"] } }
}
```

Пересчет выполняется при редактировании, не при чтении. Состояние игры, промпт GM и бой читают сохраненное число. Строки могут находиться в `ruleset.json` или `catalogs/<id>.json`; проверка содержимого требует API 1.23 для `scaled`. Разрешений и изменений нескалируемых каталогов нет.

`[sheet: op="use" name="..."]` оплачивает `mechanics.cost` и по одному использованию каждого пула строки, созданного записью. Нового объявления не нужно: команда использует уже поддерживаемые каталоги.

### API возможностей 1.24: пулы костей

`resolution` может объявлять `"kind": "dice-pool"` вместо `"dice-sum"`. Значение листа задает число костей; считаются результаты, достигшие порога. Набор определяет двойные успехи, взрывы, отмены, критические провалы, исключительные успехи и границы ситуативных поправок GM.

```json
{
  "capabilityApi": { "major": 1, "minor": 24 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json"] } }
}
```

Лист остается прежним: модификатор суммы становится количеством костей. Новых элементов листа, слотов редактора и кода пакета нет. Проверенный `ruleset.json` с `dice-pool` требует API 1.24; старые движки только с `dice-sum` отклонили бы файл целиком. Разрешений и изменений наборов суммы нет.

### API возможностей 1.25: слои и указания для мира

`layers` содержит именованные варианты, выбранные при создании и закрепленные в привязке игры. `gm.worldGuidance` читается один раз при создании мира, чтобы тот соответствовал правилам группы.

```json
{
  "capabilityApi": { "major": 1, "minor": 25 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json"] } }
}
```

Закрытый набор эффектов позволяет дописывать указания после указаний набора, удалять значения перечислений, заменять шкалу сложности шкалой того же типа разрешения и скрывать записи каталога. Новые элементы листа не добавляются, поэтому листы остаются читаемыми при любых слоях. Нет кода пакета и дополнительного вызова модели. Сторонние слои запланированы позднее. Оба поля проверенного содержимого требуют API 1.25. Без разрешений и изменений для наборов, которые их не используют.

### API возможностей 1.26–1.27: формат боя и существа

API 1.26 добавляет `combat` для бросков, целей, экономики действий, атак, способностей, состояний, концентрации, нулевого здоровья, типов урона и шкалы противников. `mechanics` описывает цели, гарантированные попадания, состояния, временные очки, масштабирование по листу и расход бюджета.

```json
{
  "capabilityApi": { "major": 1, "minor": 26 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json"] } }
}
```

API 1.27 разрешает `"holds": "creatures"`. Блоки используют `combat`: постоянное или бросаемое в начале здоровье, защиту, инициативу, характеристики и спасброски по ID листа, сопротивления, уязвимости, иммунитеты, угрозу и черты для GM. Действия могут атаковать, требовать спасброски, накладывать состояния, иметь ограниченные использования, перезаряжаться броском, выполнять цепочку действий за один бюджет или тратить собственные особые очки.

```json
{
  "capabilityApi": { "major": 1, "minor": 27 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json", "catalogs/beasts.json"] } }
}
```

Такие каталоги не объявляют `feeds` и не появляются в выборе записей листа. Версии добавляют формат и общий механизм разрешения. Сервер уже может разрешать и сохранять бои набора, обновляя листы после каждого действия. Соответствующего экрана битвы пока нет; игроки продолжают использовать существующий интерфейс боя. После проверки `ruleset.json` и объявленных `catalogs/<id>.json` установка отклоняет `combat` и новые ключи `mechanics` ниже 1.26, а `holds` и `creature` ниже 1.27. Старая строгая схема отклонила бы файл. Нет новых разрешений и изменений для наборов без этих полей.

### API возможностей 1.18: настройка Experience в мастере Game

Пакет `game-surface` может объявить `contributions.gameSurface.setup` при версии схемы 2 и API возможностей 1.18. Engine сохраняет семь обычных шагов настройки, включая **Party** (группа), цели, модели и лорбуки. Experiences предлагаются только для новых игр; повторное открытие настройки существующей игры сохраняет ее Experience и конфигурацию пакета. Пакеты без этого объявления сохраняют прежний диалог настройки.

```json
{
  "setup": {
    "seed": { "key": "seed", "label": "World seed" },
    "config": { "generate": true, "packWanted": true },
    "requires": { "enableCustomWidgets": false }
  }
}
```

Все три поля необязательны. Объявленное начальное число появляется под выбранной Experience с кнопкой **Randomize** (выбрать случайно). Пустое значение или ввод, не являющийся конечным числом, блокирует **Start** (начать). Хост записывает числовое начальное значение и объявленные константы в `experienceConfig`; `config` не может содержать ключ начального числа. После сериализации константы должны занимать не более 8 000 символов. Подпись начального числа – текст для отображения, написанный автором пакета; опустите ее, чтобы использовать локализованную подпись Engine.

Объявленное требование к виджетам задает значение по умолчанию только до изменения этого элемента игроком. Выключение Experience возвращает обычное значение по умолчанию, а явный выбор игрока сохраняется. Элемент объясняет ожидание Experience и остается доступным для изменения. Элементы настройки пространственной карты для этих Experiences скрыты, поэтому отдельный черновик карты, шаблон или конструктор не запускается.

Шаг **Lorebooks** (лорбуки) позволяет выбрать до 100 отдельных включенных записей, в том числе из неприкрепленных книг. Отключенные книги и записи, а также исключения чата учитываются. Эти идентификаторы передаются в `GameSetupConfig.activeLorebookEntryIds`. В `/game/setup` это дополнительные принудительные записи: они пропускают проверки вероятности, но сохраняют обычные лимиты токенов. Глобальный, привязанный к персонажам и прикрепленный лор по-прежнему участвует в обычном сканировании. Пакеты могут прочитать те же выбранные идентификаторы из конфигурации для собственного запроса генерации мира.

Импорт файла настройки восстанавливает установленную совместимую Experience и ее корректное числовое начальное значение, но отбрасывает произвольную конфигурацию пакета. Текущий манифест снова предоставляет константы. Существующие игры пропускают импорт Experience с пояснением. Снимки создания сохраняют название Experience и начальное число для сводки настройки.

Независимо используйте существующее объявление готовности к запуску, если мир нужно подготовить до первого хода. Объявите API 1.18 минимальной версией пакета; старые хосты не могут интерпретировать это объявление настройки.
